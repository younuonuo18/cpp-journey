## 三、今天踩的 3 个坑（比顺利的部分更值钱）

### 坑 1：仓库名拼错一个字母，导致"找不到仓库"
你建的名字是 `cpp-journe`，我们说好的是 `cpp-journey`（少了一个 **y**）。

- **现象**：命令行报 `Repository not found`，可浏览器里明明能看到那个仓库。
- **排查过程**：先查网页 → 打不开；再查 GitHub API → 旧名字返回 404；最后列出你账号下的所有仓库 → 发现真实名字是 `cpp-journe`。
- **教训**：**报错信息要当真**。"找不到"就是真的找不到——第一反应应该是"我给的地址和实际地址是不是不一致"，去对着地址栏一个字一个字核，而不是先怀疑网络。

### 坑 2：明明改好了，API 却还报 404（缓存）
改名成功之后，查新名字还是 404，查**旧**名字反而返回了新名字——这是网络中间有一层缓存在"复读"旧结果。

- **教训**：你机器上装了加速器类的网络过滤驱动，访问 GitHub 的链路里可能有缓存。以后遇到"明明改了却看不到"，先**换个参数、换个工具、等一会儿**再试，别急着重写代码。

### 坑 3：差点打开错的路径
VS 的"最近项目"列表里，`PortScanner.slnx` 那个条目指向的是**旧位置** `D:\vs\PortScanner`，而不是仓库里的新位置 `D:\cpp\w01-portscanner`。点错了就看不到任何 Git 改动。

- **教训**：**Git 是按"文件夹"管的**。项目必须在仓库文件夹里面，VS 才认得它属于哪个仓库。所以别把工程随手复制到仓库外面去用。

## 四、今天最该记住的三句话

1. **Git 管的是"文件夹"，GitHub 管的是"云端那一份"。** 本地提交 ≠ 备份成功，只有 `push` 成功才算真的上云。
2. **源码进仓库，垃圾不进仓库。** 编译产物、个人设置都不该提交——这条规则在任何语言、任何项目里都成立。
3. **提交信息是写给未来的自己看的。** 今天多花 10 秒写清楚，三个月后能省 10 分钟。

## 六、今天顺手掌握的技术细节（怕以后忘）

- **Git 命令行在哪**：你机器上 `git` 没加进 PATH，但 VS 2026 自带：
  `D:\Program Files\Microsoft Visual Studio\18\Community\Common7\IDE\CommonExtensions\Microsoft\TeamFoundation\Team Explorer\Git\cmd\git.exe`
  （平时完全用 VS 的「Git 更改」窗口，不用敲命令）
- **仓库配置**：`user.name=younuonuo18`、`user.email=younuonuo18@users.noreply.github.com`（GitHub 认可的匿名邮箱，避免暴露真实邮箱）、`core.autocrlf=false`（Windows 上关掉自动换行符转换，避免"整个文件都被修改"的假象）
- **中文乱码的真正原因**：源码保存成 **UTF-8 带 BOM** 时，MSVC 会把中文字面量编译成 **GBK** 字节；而 Windows 控制台默认就是 GBK，所以能正常显示。反过来，如果在代码里调 `SetConsoleOutputCP(CP_UTF8)`，就会把 GBK 字节按 UTF-8 解析 → **乱码**。
- **Copilot 免费计划额度**：对话约 **200 次/月**、代码补全约 **2000 次/月**（每月 22 日前后重置）。所以要**把对话额度用在刀刃上**（问概念、审代码），补全可以放心用。
- **本机性能坑**：`127.0.0.1` 上"连接被拒绝"的回环连接会等约 2 秒（加速器类 WFP 驱动导致），所以串行的端口扫描要几分钟，必须用并行 + 短超时。
